Maat · Guide to the agentic development flows

How a request becomes reviewed and verified code: skills, agents, scripts, diagrams and the decisions that shaped them.
How to read this document. This is an explanatory guide. The binding rules live in the plugin's normative files: each skill's SKILL.md (${CLAUDE_PLUGIN_ROOT}/skills/), the agent files (${CLAUDE_PLUGIN_ROOT}/agents/) and the script headers (${CLAUDE_PLUGIN_ROOT}/scripts/; the resume table, for example, lives in the header of cycle-state.sh). If they disagree, the normative file wins and this document must be fixed. The diagrams need the network the first time (Mermaid library from a CDN); offline you see their source text.
Names and paths. The plugin's skills are invoked with the /maat: prefix (for example /maat:full-implementation-cycle); here it is often omitted for brevity. ${CLAUDE_PLUGIN_ROOT} is the root of the installed plugin (in the scripts: MAAT_ROOT). Whatever depends on the project — modules, test and lint commands, production, folders — is not written in the scripts: it lives in the project's .claude/maat.json (see Configuration). The working folder is cartelle.lavoro in maat.json, by default .claude/.ai-workflow/: the one used in the examples.

1 · The specification: spec-author

An agent (Read, Grep, Glob, Write, Edit) that turns a raw request into a spec-<name>.md ready for planning. It interprets the request against the code, stops with questions on critical ambiguities and proposes alternatives when there is more than one way. It does not plan and does not implement.

Use the spec-author agent.

[change request]

Alternatively: a spec written by hand (prefix spec-, in the working folder, outside git) or text pasted directly into /plan-review-cycle, which creates the container.

2 · The plan: /plan-review-cycle

Writes the ## Implementation plan section and has it reviewed by adversarial reviewers (spec-plan-reviewer, Read/Grep/Glob only) until it is APPROVED, in a single autonomous turn with no pauses. It writes no code.

The plan cycle. A fan-out counts as one iteration, and so does each run of the gate.

The three lenses of round 1

L1 · Contract and data

missing requirements and conformance to the spec, roles and permissions, API/payload/persistence, validation, migrations, backward compatibility. It checks every nessuna implicazione (no implication), the surfaces line and the traceability table.

L2 · Fidelity to the code

every path:line exists and is the right one, which file an auto-imported component resolves to (if the framework does that), blast radius of shared files, minimality. It recounts every declared number.

L3 · Gates and tests

a minimal and sufficient test set: under-testing and over-testing are equally severe. Non-vacuity (rosso se:, "red if:"), strings searched in the test and e2e folders, satisfiable criteria, UI states.

Rules that make the cycle converge

RuleContent
Verify before applyingeach blocker/major is checked with 1 Read or 1 Grep. It is rejected only if the anchor is literally false, never by reasoning. A rejection goes into the changelog and into the lists of later prompts, and fires the gate. If in a round all findings are rejected, no delta is computed: the same producers are re-run on the same ranges, and it counts as an iteration.
Hard stops (NEEDS HUMAN DECISION)reviewer STOP · same finding in two consecutive runs · rejected finding coming back without new evidence · scope outside the spec · ambiguity the code cannot resolve · 10 iterations
Delta derived, never declaredcopy of the spec before each revision, then plan-check.sh delta. Empty diff, missing baseline or diff over the whole file = hard error: redo at full scope, never APPROVED.
Surgical revisionone minimal Edit per finding; no rewrites, no code blocks touched without reason. Lists of file:line written during revision come from a fresh search.
Recurrence tracked by the orchestratorstable key area/claim + symbol; same blocker/major in two consecutive runs of the same producer → STOP. reintrodotto (reintroduced) is a label, not a stop.
A partial review is not an approvalan APPROVED with Blocked on: or with uncovered ranges does not count; one free re-run on the uncovered part, then it counts as an iteration, then STOP.
An approved plan is not editedit is amended only by reopening it (DRAFT, delta round, gate) with a fresh budget of 10. A manual edit makes the Approved basis STALE and stops review and full cycle.
Reviewers: batched readsindependent Read/Grep/Glob in the same message, one line of text after each message with tool calls; the budget counts calls, not messages. Soft budget: ~25 in round 1, then 20 → 15 → 12 on the deltas (+50% on a blocker lead).
Orchestrator: targeted readsfirst a search, then the ranges it points to; no re-reading of unchanged ranges; re-read after every write to that file, after any command whose writes are uncertain, after a compaction. Whatever is quoted comes from a read that is still valid.

2b · The /plan-review-cycle-light variant

Same rules as the full branch (anchors, surgical revision, optional findings as notes, Approved basis, recurrence, lint, levels, floors) with two declared exceptions: it uses spec-plan-reviewer-light (concise, in depth only on permissions, DB, API, import, shared logic, auth, persistent state) and it does not take fan-out, delta or gate: every round is at full scope.

L5 · format 2: the light branch is no longer chosen by hand. After Step 1 plan-check.sh route grants it only with a plan ≤150 lines, no migration and no surface, neither detected from the files (the piano.superfici_critiche and piano.migrazioni regexes in maat.json: for example the routes folder → permessi and contratto-api, the DB schema → dati, shared packages → logica-condivisa; DELETE, DROP, TRUNCATE… → distruttiva) nor declared. Any mismatch ⇒ full branch. The implementation review always stays full.
There is never a fresh-eyes gate here: the rule "a partial review is not an approval" is the only thing between a partial round and an approved plan. On small changes the structural gain is zero: the branch exists so as not to make them worse. When in doubt, use the full branch.

3 · Implementation

By hand: you ask for the approved plan to be implemented, following it exactly, within the level. In the full cycle: the plan-implementer agent (Read, Grep, Glob, Edit, Write, Bash).

Modes

full the plan in its order — and it may arrive restricted to a block of steps · completion resumes an interrupted implementation · fix only the blocker/major findings and FAIL gates received, minimal diff, then re-runs the tests of the touched modules.

In blocks

the phase launches 2–4 implementers in sequence, one per area (backend, frontend, tests), which partition the plan's steps: each with a fresh context. pt14 In format 2 the blocks are sized by the driver: it groups the plan's #### Block sections into batches, in after: order, estimating the implementer's context from the lines of the plan and of the files the batch writes (cap FIC_LOTTO_MAX, 150k), and passes them in the prompt's LOTTI (driver) line; a block that alone exceeds the cap stays a batch of its own, declared as such. Preflight computed only once, one re-run budget per phase, reports aggregated into one. The point is to keep the context small: it averaged 353k tokens, with peaks of 595k. pt13 Lanes: in the full cycle, format 2, scripts/blocks-independent.py decides whether the blocks split into two lanes (disjoint writes:, no dependency in the real graph — explicit imports and, if maat.json declares a framework adapter (for example nuxt-autoimport), the auto-imports that framework generates, names from the path for new files —, no after: between them, no shared or generated file); then run-phase.sh launches two subsessions together under the same lock, with FIC_LANE=k (the lane's WSL copy) and FIC_WRITE_SCOPE (the guard denies Edit/Write outside its files). Rules

follows the plan to the letter, no refactoring, tests only where prescribed, only the level's gates. The commands are those of the modules in maat.json (existing environments and interpreters, never an installation); modules with copia go through test-fast.sh. Counterproofs are not its job.

Gates together, both collected

2026-09-23 two modules on disjoint substrates (for example a backend in the repo and a frontend on the WSL copy) both start in the background in the same message and are collected with BashOutput before a single outcome line is written. No background run of a module that reads the repo while its files are being modified: it reads the mutable tree and the green belongs to no version.

Tests while implementing

the smallest set of tests that reliably covers what just changed; the suite of the touched modules at the end of the block; never the whole suite under full. A run launched in the background is feedback, never gate evidence, and it does not overlap another one: the copy has a single lock.

Deviation = STOP

if a step turns out impossible or wrong against the code, it stops with the evidence: the plan is not "fixed" in the code. Migration needed → it writes the file, does not apply it, STOP.

Prohibitions (production exists)

remote hosts (ssh, rsync, scp, the release and remote-access scripts declared in guardia in maat.json) except the named exception, the plugin's test-fast.sh (copy between two local folders); DB writes; docker; git that changes state; installations; the spec; the do-not-touch files.

Reading and batching: it starts from a search or from the ranges the plan cites, does not re-read unchanged ranges, groups only independent calls (never two Edits on the same file in the same batch). Its report has a fixed form: Esito (outcome: COMPLETATO · PARZIALE · DEVIAZIONE, i.e. completed · partial · deviation), Modalità (mode), File toccati (files touched), Gate eseguiti (gates run) with the real output, Gate non eseguiti (gates not run) with the reason, Artefatti generati (generated artifacts), Deviazione dal piano (deviation from the plan), Bloccato su (blocked on). Never a gate written as PASS without running it; never /browser-qa or a browser.
